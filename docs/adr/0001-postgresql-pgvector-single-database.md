# ADR 0001. 벡터 검색을 별도 DB 없이 PostgreSQL + pgvector로 처리한다

- 상태: 채택
- 날짜: 2026-09-12

## 맥락

유사 업무 검색은 벡터 거리와 키워드 유사도를 함께 쓴다. 결과에는 요청자가 접근할 수 있는 scope의 자료만 들어가야 하고, 숨긴 자료는 개수로도 드러나면 안 된다(명세 T03). 1인 개발이고 AWS 서버 1대에 올려 비용을 최소로 유지해야 한다.

## 결정

PostgreSQL 하나에 업무 데이터·작업 큐·세션·벡터(pgvector)·trigram(pg_trgm)을 모두 둔다.

## 이유

- 권한 필터를 벡터 정렬 **전에** SQL `WHERE`로 적용할 수 있다. 전용 벡터 DB에서 상위 K개를 받은 뒤 권한으로 거르면 결과가 모자라거나 권한 밖 자료가 섞일 위험이 있다.
- 자료 upsert·동기화 커서 전진·청크 갱신을 한 트랜잭션으로 묶을 수 있다.
- 부분 unique 인덱스, JSONB, `FOR UPDATE SKIP LOCKED` 같은 기능을 작업 큐와 제약에 바로 쓸 수 있다.
- 운영할 컨테이너가 하나 줄어 서버 메모리와 비용이 줄어든다.

## 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| Qdrant 등 전용 벡터 DB | 권한 필터·트랜잭션을 두 저장소에 걸쳐 맞춰야 하고 컨테이너가 늘어난다 |
| MySQL(기존 템플릿) | 부분 인덱스·벡터 타입이 없어 명세의 제약을 그대로 옮기기 어렵다 |

## 결과

- 초기에는 ANN 인덱스 없이 정확한 거리 계산을 쓴다. 청크 수와 검색 지연을 측정한 뒤 HNSW 도입을 판단하고, 도입 시 scope 필터와 함께 결과 누락이 없는지 검증한다.
- 로컬·테스트·운영 모두 같은 `pgvector/pgvector` 이미지를 쓴다.
