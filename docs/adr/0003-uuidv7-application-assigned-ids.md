# ADR 0003. PK는 애플리케이션이 발급하는 단조 증가 UUIDv7을 쓴다

- 상태: 채택
- 날짜: 2026-09-12 (같은 날 개정: 같은 밀리초 안에서도 단조 증가)

## 맥락

- 작업 접수 API는 job·분석 ID를 202 응답에 바로 담고, 동기화는 한 트랜잭션에서 여러 행을 서로 참조하며 저장한다. INSERT 전에 ID를 알아야 편하다.
- 명세는 권한 밖 자료를 없는 자료와 같은 404로 처리하고 개수도 드러내지 않게 요구한다. 순번 ID는 값만 바꿔 넣어 자료 존재 여부를 떠보기 쉽다.
- Jira·GitHub 동기화는 수천 건을 INSERT한다. PK 인덱스 쓰기 비용이 중요하다.

## 결정

- 모든 엔티티 PK는 새 엔티티를 만들 때 `UuidV7.next()`로 발급한다(`super(UuidV7.next())`). JPA가 조회 결과를 채우는 기본 생성자에서는 발급하지 않는다.
- `UuidV7`은 한 JVM 안에서 단조 증가한다(RFC 9562 6.2 Method 2). 같은 밀리초 안에서는 74비트 난수 필드에 무작위 양수(1~2^32)를 더한다.
- 엔티티는 `Persistable`을 구현해 새 엔티티 여부를 영속화 여부로 판단한다.

## 이유

| 선택지 | 판단 |
| --- | --- |
| DB 자동 증가(IDENTITY) | INSERT 후에야 ID를 알 수 있고, 순번이라 추측 가능하다. Hibernate가 IDENTITY에서는 INSERT 배치를 쓰지 못한다 |
| UUIDv4 | 추측할 수 없지만 완전 무작위라 B-tree 곳곳에 삽입돼 페이지 분할과 단편화가 늘어난다 |
| 밀리초 안 무작위 UUIDv7 | 상위 48비트만 시각이다. 대량 발급 시 같은 밀리초 안의 순서가 무작위라 최신 리프 안에서 v4처럼 분할된다(1차 벤치마크) |
| **단조 증가 UUIDv7** | 발급 순서가 곧 정렬 순서라 인덱스 끝에만 삽입된다. 증가 폭이 무작위라 다음 값은 여전히 추측하기 어렵다 |

ID를 직접 할당하면 Spring Data `save()`가 기존 행으로 판단해 `merge`를 부르고 저장 전에 SELECT를 한 번 더 한다. `Persistable.isNew()`를 `@PostPersist`/`@PostLoad`로 관리해 새 엔티티는 INSERT 한 번으로 저장한다. 생성 시점부터 ID가 있으므로 `hashCode`가 저장 전후로 바뀌지 않는다.

## 결과

- 저장 쿼리: `PersistableSaveQueryIntegrationTest`에서 새 엔티티 100건은 SELECT 0 + INSERT 100, merge 경로는 SELECT 100 + INSERT 100.
- 인덱스: `UuidPrimaryKeyBenchmark`(100만 행, [기록](../benchmarks/uuid-primary-key.md))에서 UUIDv4 대비 리프 채움률 71.0% → 90.0%, 단편화 49.6% → 0.0%, PK 인덱스 38.2MB → 30.1MB(−21%). 시간 지표는 실행 간 편차가 커서 경향만 기록한다.
- 비용: UUID는 16바이트로 bigint(8바이트)보다 인덱스가 크다. 발급이 전역 락 하나를 거친다. 병목으로 측정되면 분할 방식을 검토한다.
- 한계: 단조 증가는 JVM 한 개 안에서만 보장한다. 서버가 여러 대면 서버 사이 순서는 밀리초 단위로만 맞는다. 같은 밀리초의 다음 ID가 이전 ID보다 크다는 사실은 드러난다(값은 약 2^32 범위에서 추측해야 한다).
- 주의: 같은 ID로 새 객체를 만들어 저장하면 UPDATE가 아니라 INSERT가 되어 중복 키 오류가 난다. 수정은 항상 조회 후 변경한다.

## 개정 이력

- 2026-09-12: 1차 벤치마크에서 밀리초 안 무작위 UUIDv7의 리프 채움률이 UUIDv4와 같게 나왔다(70.7% vs 70.5%). 생성기를 단조 증가로 바꾸고 재측정했다. 조회 때도 ID를 발급하던 필드 초기화를 생성자 발급으로 옮겼다.
