# 개발 지식 연결 서비스 (가칭)

> Jira 이슈와 GitHub PR에 흩어진 개발 경험을 연결해, 새 업무와 비슷한 과거 업무·관련 PR·경험 있는 개발자를 근거와 함께 찾아 주는 서비스

| 항목 | 내용 |
| --- | --- |
| 기간 | 2026.09 ~ 진행 중 |
| 인원 | 1인(기획·설계·백엔드·프론트엔드·배포) |
| 목표 | 해커톤 MVP → 포트폴리오로 확장 |
| 저장소 | (GitHub 링크) |

## 기술 스택

| 영역 | 기술 |
| --- | --- |
| 백엔드 | Java 21, Spring Boot 4.1, Spring Security 7, Spring Data JPA(Hibernate 7) |
| DB | PostgreSQL + pgvector(벡터 검색) + pg_trgm(키워드 유사도), Flyway |
| 인증 | 서버 세션(Spring Session JDBC) + CSRF |
| 테스트 | JUnit 5, Testcontainers(PostgreSQL), MockMvc |
| 프론트엔드 | React, TypeScript (예정) |
| 배포 | AWS 서버 1대 + Docker Compose + Nginx (예정) |

## 주요 설계 결정

### 1. 벡터 DB를 따로 두지 않고 PostgreSQL + pgvector 하나로

- 권한 필터를 벡터 정렬 **전에** SQL `WHERE`로 적용해, 권한 밖 자료가 결과에 섞이거나 결과 수가 모자라는 문제를 막는다.
- 자료 저장·동기화 커서·청크 갱신을 한 트랜잭션으로 묶는다.
- 운영 컨테이너를 하나 줄여 서버 1대·최소 비용 목표를 지킨다.

### 2. JWT 대신 서버 세션 + 요청마다 계정 재검증

- 계정 비활성화·비밀번호 변경이 로그인 중인 세션에도 **다음 요청부터 바로** 반영된다.
- 비밀번호를 바꾸면 계정의 `credential_version`이 올라가고, 세션에 저장된 값과 다르면 그 세션을 끊는다. 세션 목록을 뒤지지 않고 "다른 기기 모두 로그아웃"을 처리한다.
- 추가 비용은 인증된 요청당 PK 조회 1회다.

### 3. PK로 UUIDv4가 아니라 UUIDv7을 쓴 이유

**상황**

- 작업 접수 API는 생성한 ID를 202 응답에 바로 담아야 하고, 동기화는 한 트랜잭션에서 여러 행을 서로 참조하며 저장한다. → INSERT 전에 ID가 필요하다.
- 권한 밖 자료는 없는 자료와 똑같이 404로 응답해야 한다. → 순번 ID는 숫자만 바꿔 넣어 자료 존재 여부를 떠볼 수 있다.
- Jira·GitHub 동기화로 수천 건을 INSERT한다. → PK 인덱스 쓰기 비용이 중요하다.

**비교**

| 방식 | INSERT 전 ID | 추측 가능성 | 인덱스 삽입 위치 | 비고 |
| --- | --- | --- | --- | --- |
| DB 자동 증가(IDENTITY) | 불가 | 쉬움(순번) | 끝에 순서대로 | Hibernate가 INSERT 배치를 못 씀 |
| UUIDv4 | 가능 | 어려움 | 인덱스 곳곳에 무작위 | 페이지 분할·단편화 증가 |
| **UUIDv7(단조 증가)** | 가능 | 어려움 | 끝에 순서대로 | 16바이트 |

UUIDv7(RFC 9562)은 상위 48비트가 밀리초 시각이고 나머지는 난수다. 여기에 같은 밀리초 안에서도 값이 커지게 만들어 v4의 "추측 불가"와 순번의 "순차 삽입"을 함께 얻었다.

**구현**

- `UuidV7Generator`: 외부 라이브러리 없이 시각 48비트 + 버전·변형 비트 + 74비트 난수 필드로 만든다. 같은 밀리초 안에서는 이전 값에 무작위 양수(1~2^32)를 더한다(RFC 9562 6.2 Method 2). 시계가 뒤로 가도 값이 작아지지 않고, 여러 스레드가 동시에 발급해도 안전하다.
- `BaseEntity implements Persistable`: ID를 직접 넣으면 Spring Data `save()`가 "ID가 있으니 기존 행"으로 판단해 `merge`를 부르고 SELECT를 한 번 더 한다. `@PostPersist`·`@PostLoad`로 새 엔티티 여부를 직접 관리해 INSERT 한 번으로 저장한다.
- ID는 새 엔티티를 만들 때만 발급하고, JPA가 조회 결과를 채우는 경로에서는 생성기를 거치지 않는다.
- `equals`/`hashCode`는 ID 기준이다. 생성 시점부터 ID가 있어서 저장 전후로 hashCode가 바뀌지 않고, Hibernate 프록시도 올바르게 비교한다.

**검증**

- 단위 테스트(`UuidV7Test`): 버전·변형 비트, 같은 밀리초 안 순서, 1씩 늘지 않음, 시계 역행, 8개 스레드 40만 개 동시 발급 시 중복 없음.
- 통합 테스트(`PersistableSaveQueryIntegrationTest`): Hibernate `StatementInspector`로 실제 SQL을 수집했다. 새 엔티티 100건은 SELECT 0 + INSERT 100, merge 경로는 SELECT 100 + INSERT 100.
- 벤치마크(`UuidPrimaryKeyBenchmark`, PostgreSQL 17, 100만 행, 3회 중앙값):

| 지표 | UUIDv4 | UUIDv7 |
| --- | ---: | ---: |
| PK 인덱스 크기 | 38.2MB | 30.1MB (−21%) |
| 리프 평균 채움률 | 71.0% | 90.0% |
| 리프 단편화 | 49.6% | 0.0% |

INSERT·조회 시간도 v7이 빨랐지만(−32%, −28%), 코드가 같은 v4도 실행마다 16~31% 흔들리는 환경이라 경향으로만 본다.

**트레이드오프**

- UUID는 16바이트라 bigint(8바이트)보다 인덱스가 크다.
- 단조 증가는 JVM 한 개 안에서만 보장한다. 서버가 여러 대면 서버 사이 순서는 밀리초 단위로만 맞는다.
- 같은 밀리초의 다음 ID가 이전 ID보다 크다는 사실은 드러난다(값은 약 2^32 범위에서 추측해야 한다).
- 발급이 전역 락 하나를 거친다. 병목으로 측정되면 분할 방식을 검토한다.

## 트러블슈팅

### UUIDv7을 도입했는데 인덱스가 UUIDv4와 똑같이 듬성듬성했다

- **문제**: "시간순 ID라 인덱스에 순서대로 쌓인다"는 기대를 확인하려고 100만 행 벤치마크를 돌렸다. PK 인덱스 리프 채움률이 v7 70.7%, v4 70.5%로 같았다. 순차 삽입이라면 90% 가까이 나와야 한다.
- **원인**: 배치로 1만 개를 몇 밀리초 안에 발급하면 같은 밀리초에 수백 개 이상의 ID가 생긴다. 당시 생성기는 같은 밀리초 안의 하위 74비트가 완전 무작위였다. 그래서 최신 리프 몇 페이지 안에서 무작위 삽입이 일어나 v4와 같은 중간 분할이 반복됐다. 단편화만 줄어든 것(49.9% → 28.8%)도 "인덱스 끝 근처에서 무작위"라는 설명과 맞았다.
- **해결**: RFC 9562 6.2 Method 2로 바꿨다. 같은 밀리초 안에서는 이전 값에 무작위 양수를 더한다. +1이 아니라 무작위 간격이라 다음 ID를 추측하기 어려운 성질은 유지했다.
- **검증**: 같은 조건으로 재측정하자 v7 리프 채움률 90.0%(B-tree 오른쪽 끝 분할의 fillfactor와 같은 값), 단편화 0.0%, 인덱스 크기 −21%가 나왔다.
- **배운 점**: 명세서의 설명만 믿지 않고 인덱스 구조를 직접 측정해서 발견했다. 시간 지표는 실행 간 편차가 커서 흔들리지 않는 구조 지표로 결론을 냈다. 벤치마크도 처음에는 조회를 건별 JDBC 호출로 재다가 Docker Desktop 왕복(약 10ms)이 인덱스 비용(µs)을 덮는 것을 발견했다. 그래서 서버 내부 실행 시간(`EXPLAIN ANALYZE`)으로 바꿨다.
