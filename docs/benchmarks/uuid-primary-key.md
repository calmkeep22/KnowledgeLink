# UUID PK 벤치마크 기록

PK를 UUIDv4와 UUIDv7로 바꿔 같은 조건에서 쓰기·인덱스·조회를 비교한다(ADR 0003).

- 실행: `./gradlew benchmark` → `UuidPrimaryKeyBenchmark`, 원본 보고서는 `build/reports/benchmark/uuid-primary-key.md`
- 조건: 100만 행, 커밋당 1만 행, 3회 반복(v4·v7 순서 교대) 중앙값, 매 회차 전 `CHECKPOINT`
- INSERT 시간은 JDBC 왕복·ID 생성 포함. 조회는 서버 안에서 PK 인덱스를 5만 번 탐색한 실행 시간(`EXPLAIN ANALYZE`)
- 환경: PostgreSQL 17.11(pgvector 이미지), shared_buffers 128MB, Windows 11 + Docker Desktop, 클라이언트 5코어

수치는 실행 환경에 따라 달라진다. 비교는 같은 실행 안의 v4·v7 사이에서만 의미가 있다.

## 측정 방법을 바꾼 이유

조회 시간은 처음에 JDBC로 PK를 한 건씩 5만 번 조회해 쟀다. v4와 v7의 차이가 거의 없게 나왔는데, Docker Desktop을 거치는 왕복 지연(약 10ms)이 인덱스 탐색 비용(µs)을 덮고 있었다. 그래서 서버 안에서 인덱스를 탐색한 실행 시간(`EXPLAIN ANALYZE`)으로 바꿨다. 측정하려는 비용이 다른 비용에 가려지지 않는지 먼저 확인해야 한다.

## 1차 (2026-09-12): 같은 밀리초 안에서는 무작위인 UUIDv7

| 지표 | UUIDv4 | UUIDv7 | v7 기준 차이 |
| --- | ---: | ---: | ---: |
| INSERT 시간(ms) | 59717 | 57723 | -3% |
| WAL 생성량(MB) | 224.0 | 214.8 | -4% |
| PK 인덱스 크기(MB) | 38.5 | 38.4 | -0% |
| 리프 페이지 수 | 4899 | 4889 | -0% |
| 리프 평균 채움률(%) | 70.5 | 70.7 | +0% |
| 리프 단편화(%) | 49.9 | 28.8 | -42% |
| PK 조회 1건당(µs, 서버 내부) | 13.97 | 14.35 | +3% |

**해석**

- 예상과 달리 **리프 채움률이 v4와 같다**(70%). 키가 순서대로 들어오면 PostgreSQL은 가장 오른쪽 페이지를 분할할 때 왼쪽 페이지를 거의 가득(fillfactor 90%) 남기므로 채움률이 90%에 가까워야 한다.
- 원인 추정: 배치로 1만 개를 몇 밀리초 안에 만들면 같은 밀리초에 수백 개 이상의 ID가 생긴다. 당시 `UuidV7`은 같은 밀리초 안의 하위 74비트가 완전 무작위였다. 그래서 최신 리프 몇 페이지 안에서 무작위 삽입이 일어나 v4와 같은 중간 분할이 반복된 것으로 보인다.
- 단편화가 줄어든 것(49.9% → 28.8%)은 이 추정과 맞다. 분할로 생긴 새 페이지가 여전히 인덱스 끝 근처에 모인다.
- PK 조회 1건당 시간은 오차 범위 안에서 같다. 조회 자체가 빨라지는 것은 아니라는 예상과 일치한다.
- INSERT·WAL 차이가 작은 것은 인덱스(38MB)가 shared_buffers(128MB)에 모두 올라가 무작위 삽입의 디스크 비용이 드러나지 않는 조건이기 때문으로 본다.

**조치**: 같은 밀리초 안에서도 값이 커지도록 생성기를 RFC 9562 6.2 Method 2(monotonic random)로 바꾼다. 같은 밀리초의 다음 값은 이전 값에 무작위 양수(1~2^32)를 더해 추측하기 어렵게 유지한다.

## 2차 (2026-09-12): 단조 증가 UUIDv7

| 지표 | UUIDv4 | UUIDv7 | v7 기준 차이 |
| --- | ---: | ---: | ---: |
| INSERT 시간(ms) | 69154 | 47000 | -32% |
| WAL 생성량(MB) | 223.7 | 209.8 | -6% |
| PK 인덱스 크기(MB) | 38.2 | 30.1 | -21% |
| 리프 페이지 수 | 4863 | 3832 | -21% |
| 리프 평균 채움률(%) | 71.0 | 90.0 | +27% |
| 리프 단편화(%) | 49.6 | 0.0 | -100% |
| PK 조회 1건당(µs, 서버 내부) | 18.27 | 13.11 | -28% |

**해석**

- 원인 추정이 맞았다. 같은 조건에서 v7의 리프 채움률이 70.7% → 90.0%로 올랐고 단편화는 28.8% → 0.0%가 됐다. 90.0%는 오른쪽 끝 페이지 분할 시 남기는 B-tree fillfactor(90)와 같다. 모든 키가 인덱스 끝에만 삽입됐다는 뜻이다.
- 인덱스가 촘촘해져 같은 100만 행의 PK 인덱스가 21% 작다(38.2MB → 30.1MB, 리프 4863 → 3832페이지). 같은 메모리에 더 많은 키를 올릴 수 있다.
- **시간 지표는 확정하지 않는다.** 코드가 같은 v4도 1차 → 2차에서 INSERT 59.7초 → 69.2초(+16%), 조회 14.0µs → 18.3µs(+31%)로 흔들렸다. 이 환경(Windows + Docker Desktop)의 실행 간 편차가 커서 INSERT −32%, 조회 −28%는 개선 경향으로만 기록한다.
- 결론은 실행마다 흔들리지 않는 인덱스 구조 지표(채움률·단편화·크기)로 낸다.

**다음에 확인할 것**: 반복 횟수를 늘려 분산을 함께 기록하고, Linux 서버에서 인덱스가 shared_buffers보다 큰 조건(실제 운영 규모)도 측정한다.
